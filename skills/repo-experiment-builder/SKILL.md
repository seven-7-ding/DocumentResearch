# Research repository construction

Inspect the current directory and applicable AGENTS.md instructions first. Determine whether actual source code exists; documentation alone does not make an existing codebase. For an empty codebase, locate implementation requirements in existing Markdown/text documents (often codex-prompt.txt), read them without modifying the prompt, and implement their requested functionality. For existing code, preserve unrelated work and apply the same conventions below unless the user explicitly exempts some or all of them.

## Required conventions

- Create `logdir/`. Every experiment/run gets its own unique subdirectory. Keep organization flat when practical, or use configuration groups followed by a unique run directory. ALL generated experiment files belong inside that run directory: logs, datasets generated by the run, models, plots, screenshots, test outputs, downloads, staging checkouts, caches and temporary files. Set subprocess working directories, temp/cache variables and output parameters accordingly; disable Python bytecode when appropriate. Never spill experiment artifacts into the repo root, source folders or OS temp. Source files and intentional deliverables are not experimental artifacts. Explicit requested deployment copies may leave the local run directory; do not upload unrelated run artifacts.
- Create `auto_script/` with simple `.bat` launchers on Windows or `.sh` on Linux. Put important adjustable parameters together at the top or in one clearly named shared config. Launch from any working directory with one command, preserve arguments and propagate failure exit codes.
- Use only the existing conda environment `bit` by default. Do not create virtual environments or download large extension packages. If bit or a necessary dependency is missing, explain the concrete blocker; do not silently substitute another environment.
- Maintain root `codex-executor.log`, retaining at most five latest entries plus one explicitly marked important historical entry. Each entry is one concise timestamped record. Never store secrets in logs.
- Maintain root `task_checklist.md` containing ONLY task checkboxes, including requirements/constraints and completion criteria as checkable tasks. No headings, narrative sections, progress logs or execution history.
- Leave `codex-prompt.txt` untouched. Ignore it, `logdir/`, `codex-executor.log`, and `task_checklist.md` in Git. Ignore legacy executor logs as well when present.
- If credentials are needed, use an ignored `.env` (or an existing credential manager); `.env` must exist for the repo's local secret configuration. Commit only a placeholder `.env.example`. Never print, commit or upload secrets. Check tracked files as well as ignore rules; ignoring an already tracked secret does not remove it from history.

Use available `auto-cli-agent` and `task-checklist-loop` skills for autonomous implementation and ongoing requirements. The explicit user conventions above override their alternative log filename and progress-log templates. Do not create duplicate executor logs.

## Completion

Implement and run the actual user-requested experiments/workflows to completion, beyond smoke tests. Validate observable end-to-end outcomes with real inputs where available, including consequential failure paths. Keep evidence within that run's logdir. Distinguish tested local outcomes from actual remote deployment or experiment completion. Record genuine external blockers as unchecked tasks, and report exactly what is missing rather than claiming success.
